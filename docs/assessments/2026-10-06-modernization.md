## Scope and evidence limits

Assessment only. No firmware edits, dependency upgrades, push, PR, flashing, uploads, or live-network/device changes. Initial tracked worktree was clean. No AGENTS.md or CLAUDE.md found in repository or inspected ancestor paths. README and PlatformIO configuration were read; local secret/config values are deliberately omitted. Ignored secret files remain untouched. No checked-in tests or CI were found. CodeRabbit CLI is unavailable; this is a manual source/dependency review, not a CodeRabbit result.

Incident context is user-provided, not independently re-measured here: garage DRUINO-WORKSHOP fell from 220–247 readings/day to 54 on October 5 after an October 4 eero change; broker logs show k60 timeouts. Office also times out around 92 seconds yet reports 288/day. Garage HTTP samples are fresh and ping has 0% loss. Eero causality remains unproven. A five-minute schedule gives 288 expected opportunities per 24 hours per metric (not a guarantee of delivery or a count of combined temperature/humidity messages).

Strongest explanation for recurrent keepalive timeouts is missing MQTT servicing (F1). This explains why both devices time out and why an office device can still produce 288/day by reconnecting every publish. It does not, by itself, explain the garage's new loss of readings. Publish failure, reconnect delay, DHT scheduling, buffer corruption, weather blocking, differing binaries/configurations, broker/consumer behavior and network changes remain competing explanations. Ping verifies ICMP reachability, not MQTT delivery. The HTTP “Sample Time” is actually request time (F8), so freshness inferred solely from that field is unreliable. Live firmware equivalence to this checkout is unverified.

## Findings

Severity: Critical = deterministic memory corruption or remote firmware integrity risk; High = major availability/data-loss/security risk; Medium = correctness, reproducibility or operational weakness; Low = maintainability. Security impact depends on network reachability; no exploitation or CVE audit was performed.

| ID | Severity | Evidence | Impact and recommendation |
|---|---|---|---|
| F1 | High | `src/WeatherStation.cpp:384,414–458,579–585,626–630`; `include/settings.h:118` | Keepalive is 60s; publish interval is 300s. `client.loop()` runs only inside the disconnected branch after reconnect, never routinely while connected. PubSubClient sends PINGREQ/processes PINGRESP from loop. Regular disconnects around 90s are consistent with broker grace, not proof of RF failure. Service MQTT every main-loop iteration, independently of display budget; measure maximum service gap. Increasing keepalive alone hides the defect. |
| F2 | Critical | `src/WeatherStation.cpp:170–175,594–599,761–771` | Two 18-byte timestamp arrays receive 19 printable characters plus NUL with `snprintf(...,20,...)`: two-byte stack overflow for normal dates. Default 12-hour overlay writes 11 printable characters plus NUL into 11 bytes using sprintf: one-byte overflow. Use adequate arrays, `sizeof` bounds and check truncation. Add host sanitizer checks for both time formats. |
| F3 | High | `src/WeatherStation.cpp:160,587,607,616` | Global mqttmsg is 50 bytes but snprintf is told 75. Long sensor/device identifiers can corrupt globals. This is a definite incorrect bound, though actual overflow depends on payload lengths. Use `sizeof(mqttmsg)`, reject truncation, and verify full packet fits PubSubClient buffer. |
| F4 | High | `src/WeatherStation.cpp:422–425,541–576,822–828` | DHT-ready flag is set but never cleared. After first timer tick, reads repeat whenever UI is FIXED; DHT library can wait internally between reads. This repeatedly blocks application services and increases CPU/sensor load rather than sampling once a minute. Clear due flag once consumed and schedule retries by elapsed milliseconds. |
| F5 | High | `src/WeatherStation.cpp:552–557`; local `.pio/libdeps/workshop/DHTNew/dhtnew.h:78–79`, `dhtnew.cpp:121–126,205` | lastRead() is absolute milliseconds since boot, not age. Comparison to 2500 only protects very early startup, not inter-read spacing. read() return is ignored; lower-bound validity checks do not enforce finite values, DHT22 upper limits or coherent pairs. Current library normally invalidates errors, so stale acceptance is conditional on library behavior/config. Record return codes; use wrap-safe `millis()-lastRead()`, nonblocking read option, explicit sensor type, and finite/range checks. Publish paired readings with acquisition time and validity. |
| F6 | High | `src/WeatherStation.cpp:639–667,581–585,627–630` | MQTT reconnect retries forever, with 3s delay and synchronous connect; broker outage blocks DHT, web, OTA, UI and publishes indefinitely. No Wi-Fi gate/backoff. Scheduled display callback can also enter reconnect via setDisplayOff → updateMQTTpresence. Use a bounded one-attempt state machine with jitter/backoff, Wi-Fi status gate and bounded socket timeout; callbacks should only enqueue events. delay/yield may feed watchdog but do not service application MQTT/HTTP/OTA. |
| F7 | High | `src/WeatherStation.cpp:611,620,623,633–635` | All publish return values are discarded and due flag cleared even on failure. QoS0 provides no broker delivery acknowledgement; temperature can succeed while humidity fails. Add attempt/success/failure/state counters, one bounded pending latest sample, and retry policy. If durable delivery is required, evaluate QoS1-capable client or application ACK with sequence/deduplication; do not claim publish=true proves database ingestion. |
| F8 | Medium | `src/WeatherStation.cpp:167–191,593–599,605–620,724–731` | HTTP and MQTT timestamp the request/publish, not DHT acquisition. Display can retain old numeric values while validity is false. Expose last valid sample time, age, validity/error counts and publish times distinctly; mark stale display data. |
| F9 | High | `src/WeatherStation.cpp:512–538,417–419`; local `.pio/libdeps/workshop/ESP8266 Weather Station/src/OpenWeatherMapCurrent.cpp:49–90` | Synchronous weather request blocks main loop, followed by explicit 1s delay. Dependency uses plaintext HTTP and logs full API-key-bearing URL. Its 10s check is inside client.available(): connected-but-silent peer can spin yielding indefinitely, and delayed available response can trigger ESP.restart. Forecast path needs same audit. Add outer wall-clock deadline, bounded reads and graceful failure; isolate optional weather from indoor telemetry. Use verified HTTPS and redact URLs. Treat this as cached dependency behavior, not measured device stalls. |
| F10 | Critical | `src/WeatherStation.cpp:372–378` | ArduinoOTA is enabled without setPassword/setPasswordHash. A reachable compatible OTA peer may replace firmware without application authentication. Add authentication and restrictive management access; assess signed firmware for stronger integrity. Preserve physical recovery path before rollout. |
| F11 | High | `src/WeatherStation.cpp:157–158,381,646`; `include/settings.h:109–114` | MQTT is plaintext port 1883, connect supplies client ID only, no credentials or last will. LAN peers with broker access may observe/spoof data; duplicate client IDs can evict devices. Enforce broker ACLs/per-device identity and authentication; consider TLS after measuring ESP8266 RAM and CA/time requirements. Add availability will and unique stable client IDs. Broker exposure/ACLs were not inspected. |
| F12 | Medium | `src/WeatherStation.cpp:311–349,439–443,403–407` | Provisioning autoConnect has no supplied AP password; portal is limited to 300s but restarts can repeat exposure. HTTP endpoints have no auth/TLS and disclose topics/chip ID/build date. Hostname set after autoConnect; subsequent Wi-Fi recovery relies on core defaults with no disconnect-reason tracking. Later Wi-Fi wait is unbounded. Use protected/time-limited provisioning, set hostname before connection, explicit bounded reconnect policy and management-network restrictions. HTTP/OTA servicing is gated by positive UI budget and can starve. |
| F13 | Medium | `include/settings.h:168,178–182`; `src/WeatherStation.cpp:181–186,564` | DHT value is always converted to Fahrenheit while METRIC controls output unit labels and IS_METRIC separately controls weather/display. A metric build can publish Fahrenheit labeled Celsius. Use one unit policy and test all compile-time variants. Default current policy is imperial, so this is latent in other configurations. |
| F14 | Medium | `platformio.ini:11–12,22,28–36`; `.gitignore:1–4` | Unpinned platform, floating Git libraries/ranges and required ignored environments/secrets prevent reproducible clean builds. Dependency metadata disagrees with cached manifests (see below). Track nonsecret build profiles and secret template, pin verified releases/SHAs and platform; validate in clean isolated cache. Secret paths are ignored and not tracked in current index; history was not scanned, so absence of historical leaks is not established. |
| F15 | Medium | `src/WeatherStation.cpp:177–190,196–199,205–223,728–731,778–779`; `platformio.ini:24` | Dynamic String concatenation in handlers and frequent rendering can create heap pressure/fragmentation; 160MHz/30FPS display work and interrupt-disabled DHT reads add load. No measured heap/reset/loop latency evidence. Record free heap, largest block/fragmentation, reset reason and loop/service gaps; reduce churn with reserve/bounded formatting only if measurements justify it. Do not diagnose watchdog resets from source alone. |
| F16 | Medium | `src/WeatherStation.cpp:216,257–273,508` | Empty `#elif` breaks a build with PIR disabled; both forecast flags create duplicate frames definitions. OTA progress divides by total/100, potentially zero for very small total. Validate supported feature matrix and use safe arithmetic. These are static findings; compiler never reached source. |
| F17 | Low | `src/WeatherStation.cpp:52–854`; `README.md:29` | Single firmware unit mixes transport, sensor, weather, display and HTTP; stale comments (5s vs 3s retry) and README calls broker Kafka. No tests/CI. Keep small explicit functions/modules and correct operational README; avoid wholesale architecture rewrite. Timer callbacks should do minimal flag/event work; volatile alone would not solve event loss or callback reentrancy. |

## Phased modernization plan (proposed only)

Effort estimates are engineering days excluding unattended soak and access delays. Preserve existing semicolon MQTT schema/topics until consumer migration is approved.

| Phase | Work | Tests and acceptance | Effort | Risk and rollback |
|---|---|---|---|---|
| 0: reproducible baseline | Capture deployed firmware identity/config privately; repair build execution in isolated compatible environment; pin exact known dependencies, provide nonsecret profiles/template, archive known-good binary and build manifest. Collect broker connect/disconnect/publish counts versus consumer ingestion, reset reasons and Wi-Fi observations. | All six profiles compile/link; capture RAM/flash margins. Compare garage/office cadence using same timezone, metric and full-day window. Verify independent HTTP observation contains actual acquisition age once instrumentation exists. | 1–2 days | Cache drift may make baseline differ from deployed firmware. Do not flash until recovery binary exists; revert build-profile commit/pins and retain original artifact. |
| 1: correctness and service availability | Fix all buffer bounds, DHT-ready lifecycle/unit policy, separate acquisition timestamp; call MQTT loop regularly; replace infinite reconnect with bounded scheduled attempts; inspect publish return and preserve pending sample. Avoid adding new framework. | Host ASan/UBSan formatting checks at max identifier lengths, both clock modes, rollover and invalid/nonfinite sensor cases. Fake clock/client tests for reconnect, timer consumption, backoff and pending-sample policy. Bench broker outage 30min, Wi-Fi outage 10min, restoration, partial publish failure and duplicate IDs. HTTP/sensor must continue during MQTT outage; service gap target <1s during normal operation and always safely below keepalive. | 2–4 days | Timing changes can expose hidden display or consumer assumptions; timestamp semantics must be documented. Small independent commits; restore archived binary/config physically if OTA fails. |
| 2: weather and health isolation | Bound optional weather total duration, remove fatal restart on HTTP delay, move retries out of service-critical path. Add local diagnostic counters/loop latency/heap/reset reason and acquisition freshness. Reduce String churn only if observed. | Silent TCP peer, slow/dribbled response, malformed JSON, DNS/API outage, DHT unplug/replug, 72h bench soak. No indefinite application stall or weather-triggered reboot; no declining largest heap block trend; explain all missing publish opportunities. | 2–3 days + soak | Dependency patch/upstream change alters weather behavior and memory. Keep original dependency SHA and independent rollback; failure should show stale weather while telemetry continues. |
| 3: security | OTA authentication/access limits, protected provisioning, broker per-device ACL/auth; redact API logging and evaluate weather HTTPS, MQTT TLS and signed OTA within measured memory budget. | Reject unauthorized OTA/MQTT and wrong-topic writes; verify TLS trust failures, bad time/expired cert, recovery path and RAM margin with OTA. Negative provisioning/HTTP access tests on isolated bench. | 2–4 days | Credential/TLS rollout may strand devices. Stage broker ACL/auth support before firmware enforcement; retain physical serial recovery and secure archived configuration. Never publish secrets in diagnostics. |
| 4: controlled validation and maintenance | Small module extraction only where useful; CI compile matrix/host tests, documented setup and releases. Future approved rollout one spare/canary then garage then office. | 72h canary with stable heap and no keepalive disconnects, up to 288 expected per-metric samples/day minus documented outages; correlate publish successes with broker and storage. Compare firmware-only change with stable network settings before any controlled eero A/B experiment. | 1–2 days + soak | A/B changes confound diagnosis. Freeze network during firmware test; revert canary binary/config if regression. No broad rollout without measured evidence. |

Total: approximately 8–15 engineering days plus soak time. Phase 1 has the highest immediate reliability value; critical security/memory items should not wait for optional refactoring. QoS1/durable queues and TLS are decisions driven by delivery requirements and measured resource headroom, not mandatory dependency replacement.

Rollback rule for every future phase: separate commits, versioned manifest and checksum of known-good binary, private config backup, physical serial access, one device at a time, explicit abort thresholds (service gap, reset, publish/ingestion drop, heap exhaustion). Assessment branch contains documentation only; a future implementation must be separately authorized.
