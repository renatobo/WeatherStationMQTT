## Bounds and failure behavior

- Eight-second overall request budget; 1.5-second inactivity budget. DNS/TCP allow
  one second each; TLS handshake allows four seconds. SDK/body operations use
  shorter waits. Synchronous operations can finish after a budget check; the
  budget is checked again before committing the cache.
- The TLS client verifies the hostname, certificate chain and dates against
  ISRG Root X1, uses TLS 1.2 and rejects redirects. It never enables insecure
  mode. An unsynchronized clock defers retrieval. TLS record buffers are bounded
  at 8192 receive/512 transmit bytes; oversized records fail closed.
- The response body is bounded at 2048 bytes plus its terminator; plaintext reads
  are capped at 8192 bytes including HTTP framing. The SDK handles content-length
  and chunked transfer framing; requests explicitly prefer identity encoding.
- ArduinoJson uses fixed allocation, limited nesting and filtered fields. The
  full response must pass type, unit, date, temperature, WMO-code and forecast-array
  checks before the complete snapshot is swapped. Invalid/partial data preserves
  the last good snapshot and marks it stale. No weather failure calls ESP.restart.
- Header/body waiting pumps MQTT, DHT, HTTP, OTA and display services. Initial
  DNS/TCP/TLS setup remains synchronous and bounded; this is not an asynchronous
  TLS implementation. Weather is deferred while MQTT is offline or memory is low.

The pinned SDK resets its own handshake timeout internally. Merely calling the
wrapper's setTimeout would not bound it. `scripts/bounded_tls.py` verifies the
original SDK file SHA256 and creates the bounded source in each build directory.
The shared framework cache is unchanged. The generated source retains its original
license and is included in private recovery archives.

## Diagnostics and tests

`/info` adds weather state, HTTP/TLS/validation stage, attempt/success/failure counts,
request durations and cache age. It also reports sampled free-heap minima, largest
free-block minima, fragmentation, continuation-stack margin and reset details.
The HTML output reserves capacity to reduce reallocations. Heap minima are sampled
at application/HTTP service points and do not claim continuous allocator coverage.

Both host suites passed with C++11, -Wall/-Wextra/-Werror, ASan and UBSan. Weather
checks cover valid imperial/metric data, malformed/truncated/trailing input, wrong
units, missing fields, numeric strings, date normalization, WMO mapping, preserved
cache, silent/dribbled receive deadlines, oversize input, fixed-buffer bounds and
millis rollover. They model policies and decoder behavior rather than real radio
or TLS faults. The live checker additionally requires a fresh validated weather
response, which detects integration failures that host-only tests cannot.

All six profiles passed; metric/24-hour/forecast and long-forecast feature builds
passed. The new dependency is ArduinoJson 6.21.6. The unused Weather Station and
JsonStreamingParser dependencies were removed. Pinned simpleDSTadjust precedence
and PubSubClient signedness warnings remain recorded in
[build evidence](2026-10-06-phase2-builds.json); application warnings are not suppressed.

## Canary findings and corrections

An early candidate ran for roughly 2h40m with one MQTT connection/no disconnects,
31 scheduled pairs/no skipped or failed publications, and no observed reboot.
Weather did not succeed. The failure was investigated rather than treating healthy
telemetry as proof of weather correctness.

Connection-stage diagnostics identified overly tight 250ms TCP setup. Measured
LAN-server TCP setup was 179ms before ESP/Wi-Fi overhead, so setup limits were
raised within the overall budget. A later HTTP 200 exposed a separate integration
bug: the custom Stream did not advertise writable capacity, so SDK writeToStream
returned an empty body. The capacity contract was fixed and the new live weather
verification added. These candidates were not published as tags or rolled to office.

The corrected workshop image retrieved verified HTTPS data successfully in 3166ms,
with TLS error 0 and no validation error. Idle free heap recovered to about 30KB;
sampled minimum free heap was 9672 bytes and minimum largest block 7320 bytes.
The maximum MQTT service gap was 2779ms, reflecting synchronous TLS setup and
remaining well below the 60-second keepalive. These are measured short-canary
results, not a guarantee of sub-second service during every connection.

Final workshop/office rollout evidence is appended after verification. Raw replies,
broker addresses, configuration and firmware binaries remain in ignored `.recovery/`.

## Remaining validation and next phase

Physical Wi-Fi/sensor removal tests, malicious/silent TLS-peer bench tests and a
72-hour soak were not performed. No eero, broker, collector or live network settings
changed. Continue measuring heap/block trends and correlate sensor writes with
storage during the soak. Root certificates and the SDK overlay require review
when dependencies or the provider's chain change.

Management authentication, protected provisioning, MQTT authentication/TLS and
signed updates remain Phase 3. Concurrent TLS resource use must be evaluated against
the measured weather-request heap low-water marks. The v0.2.0 bootable images and
private configuration remain available for rollback; serial recovery is not rehearsed.

## Final workshop verification

The corrected image passed the full live image/HTTPS/data check. Two scheduled weather requests succeeded with no TLS or validation error; the second took 2919ms (maximum 3166ms). Sampled minimum free heap fell to 8136 bytes and minimum largest block to 4120 bytes during overlapping service work, then idle free heap recovered to about 30KB with the largest free block at 26096 bytes. These low-water marks constrain concurrent TLS work; they are not hidden.

MQTT remained at one connection/no disconnects, with two scheduled pairs/no skips, five writes/five successes/no failures including presence, and maximum service gap 2779ms. All four observed metric messages matched MariaDB exactly. Direct HTTP remained responsive across the polls. See [machine-readable workshop evidence](2026-10-06-phase2-workshop.json).

A separate fresh-cache build with placeholder configuration also passed, verifying dependency resolution and the generated SDK overlay without relying on the existing cache.
